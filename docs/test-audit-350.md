# Test-suite audit for issue #350 ("prevent test bloat")

First pass, read-only. Audited at commit `ddb6618` with the `test-anti-patterns` and `audit-tests` skills, one auditor per feature folder, every `[Fact]`/`[Theory]` given a ledger row. Nothing in the suite was changed; this document is the evidence and the proposed batches.

## 1. What the measurements say

| Measurement | Value | Source |
|---|---|---|
| Test files / lines | 204 / 40,669 | `PersonalFinance/tests/PersonalFinance.Tests` |
| `[Fact]` / `[Theory]` / `[InlineData]` rows | 1,392 / 205 / 773 | grep |
| Test cases executed | 2,305 (2,304 pass, 1 skipped) | local run and CI log, identical |
| Local wall time | 31 s | `dotnet test` |
| Summed per-test time | 177 s (parallel collections) | TRX |
| Cases under 5 ms | 1,278 | TRX |
| CI "Execute test suite" step | 37 s | run 40429146384 |
| CI Build & Test job | 2 min 48 s (build 60 s, tests 37 s, publish check 26 s) | same run |
| CI E2E Browser Tests job (longest job) | 3 min 22 s (build/setup ~105 s, `ui-test.js` 93 s for 140 checks, `api-test.js` <1 s for 15) | same run |
| CI push-to-deploy wall time | ~6 min | last three runs |

Conclusions that frame everything below:

1. **The xUnit suite is not what slows CI.** It costs 37 s of a 6-minute pipeline. The longest job is the Playwright one, and most of that is building the solution a second time and starting two hosts, not the checks themselves.
2. **Nothing is silently skipped.** CI executes the same 2,305 cases as a local run. The one `Skip` is a PowerShell-dependent Bicep test whose skip reason is stale (see Infrastructure M4).
3. **Local wall time is set by one class.** `ResearchSectorsGroupingTests` runs 28.9 s serially (six tests) out of the 31 s suite, because a production rate limiter sleeps in real time over a frozen test clock (Research M1). Fixing that clock, not deleting tests, is the speed win.
4. **The real bloat cost is maintenance and false confidence**, not minutes: the same contract proved at two or three layers, a few tests whose expected value comes from the code under test, and a handful of wall-clock dependencies that will go red on a calendar date.

Slowest classes (summed ms, cases): ResearchSectorsGroupingTests 28,929 (6); ResearchFundsServiceTests 19,184 (36); ResearchServiceTests 11,130 (18); PriorityWalkSchemaTests 7,872 (21); InternalApiClientRegistrationTests 4,584 (5); AccountDeletionServiceTests 4,142 (16); DataExportServiceTests 3,488 (12); DataSourceRemovalTests 3,286 (11).

## 2. Suite-wide verdict

The suite is well written. Oracles are exact decimals with the arithmetic in comments, regression tests cite their issue, privacy and account isolation are tested as behaviour, fakes are hand-written over real clients rather than mocks, and the Architecture tests enforce ADRs 0007 and 0008 by reflection. No test is assertion-free; the mechanical "no inline Assert" hits were all helper methods (`AssertValid`, `AssertInvalid`, rendering helpers) that assert exact values.

Totals across the folders audited so far are in section 10.

## 3. Research/ (26 files, 263 methods, 364 cases, 73.5 s summed)

Verdict: well written. 0 Critical, 1 High, 2 Medium, 10 Low. Evidence rows: 6 Remove, 5 Combine, 5 Repair.

**H1 wall clock.** `CompanyProfileFixtureTests.cs:116` defaults `PressReleasesOfFixture` to `DateTimeOffset.UtcNow`, and `FixtureSecCompanyClient` dates its 8-Ks relative to today, so two tests test a new unpinned date every run. Fix: default to `new DateTimeOffset(2026, 10, 24, 12, 0, 0, TimeSpan.Zero)`, the instant `LookUpFixture` already uses. Expected values unchanged.

**M1 real-time SEC rate-gate sleeps (the speed finding, ~120 cases in 8 classes).** Tests build `SecRequestGate` over a frozen `FixedTimeProvider` (ResearchSectorsGroupingTests:30, ResearchServiceTests:34, ResearchFundsServiceTests:45/602/892, ResearchFundFactsServiceTests:40, ResearchMacroServiceTests:36, ResearchWorldServiceTests:43, CompanyProfileServiceTests:92, CompanyPressReleasesServiceTests:159). `WaitAsync` sets `_nextAllowed = now + 1 ms`; the clock never moves, so every request after the first waits 1 ms through a real system timer (about 15 ms per tick on Windows; measured 1,603 ms for 100 calls).
